## 1. Контекст системи (System Context)

### 1.1 Призначення

Kurin надає кільком екземплярам одного Java-сервісу (типово 3–5) узгоджений спільний стан без окремого кластера
координації. Кожен екземпляр містить вбудований вузол Raft; екземпляри утворюють кластер консенсусу зі
статичним складом. На цьому стані побудовано чотири примітиви: розподілені блокування з маркером огородження,
задачі лідера, одноразові задачі за розкладом і узгоджену інвалідацію багаторівневого кешу. Окремий модуль
маршрутизації обирає вузол бази даних (primary, репліка, шард) для кожної транзакції.

### 1.2 Межі системи (Scope)

**Входить у систему:** модулі `core`, `kurin-locks`, `kurin-tiered-cache`, `kurin-data-routing`, Spring Boot
starters, адаптери Actuator для Spring Boot 3 і 4.

**Не входить у систему:** бізнес-логіка застосунку; сервер бази даних; зовнішнє сховище кешу (застосунок
реалізує інтерфейс `ExternalCacheStore`); система моніторингу (Prometheus, Grafana); засоби автентифікації
HTTP-запитів застосунку (Spring Security); оркестратор контейнерів.

### 1.3 Зовнішні сторони та інтерфейси

| Сторона | Тип | Інтерфейс із системою | Протокол |
| :--- | :--- | :--- | :--- |
| Розробник застосунку | Person | Java API (`KurinNode`, `KurinLockManager`, `KurinTemplate`), анотації, властивості `kurin.*` | внутрішньопроцесні виклики |
| Оператор (DevOps) | Person | конфігурація, `/actuator/health`, `/actuator/kurin`, метрики | HTTPS (через Actuator застосунку) |
| Екземпляр-партнер (peer) | System | протокол вузлів Kurin | TCP + TLS 1.2/1.3 (mTLS), кадри Netty, Kryo |
| PostgreSQL primary / репліки | System_Ext | JDBC через `KurinRoutingDataSource` | PostgreSQL wire protocol / TCP |
| Зовнішнє сховище кешу | System_Ext | `ExternalCacheStore` (реалізує застосунок, напр. Redis) | визначає реалізація (RESP / TCP для Redis) |
| Система моніторингу | System_Ext | `/actuator/prometheus`, `/actuator/health` | HTTP pull |
| Клієнт HTTP-застосунку | Person / System_Ext | заголовок `X-Kurin-Consistency` (маркер узгодженості) | HTTP(S) |

### 1.4 Припущення та залежності

- Збій вузлів – аварійна зупинка (crash-recovery); візантійські збої не розглядаються.
- Годинники вузлів можуть розходитися; на гарантії безпеки журналу це не впливає, гарантія `LEASE`-читань
  залежить від обмеженого дрейфу годинників (див. [SRS-FUN-07](#srs-fun-07)).
- `fsync` диска повертає керування лише після запису на носій.

Кожна вимога атомарна: одна системна дія, одна умова, один спостережуваний результат.

## 4. Обмеження проєктування (Design Constraints)

| ID | Обмеження | Наслідок для проєктування |
| :--- | :--- | :--- |
| <a id="srs-con-01"></a>SRS-CON-01 | Фреймворк є бібліотекою в процесі застосунку і не відкриває власних HTTP-портів. | Інтерфейс керування – лише через Actuator застосунку; автентифікацію HTTP (OAuth2 / JWT) забезпечує застосунок. |
| <a id="srs-con-02"></a>SRS-CON-02 | Модулі `core`, `kurin-locks`, `kurin-tiered-cache`, `kurin-data-routing` не залежать від Spring. | Spring-специфічний код – лише в starters. |
| <a id="srs-con-03"></a>SRS-CON-03 | Склад кластера статичний. | Зміна складу – перезапуск з новою конфігурацією; joint consensus не реалізується. |
| <a id="srs-con-04"></a>SRS-CON-04 | Стан Raft змінюється лише в одному потоці `kurin-raft-<port>`. | Таймери, RPC і запити клієнтів передаються в цей потік; обробники команд не блокують. |
| <a id="srs-con-05"></a>SRS-CON-05 | Обробники команд детерміновані; час – лише з `KurinCommandContext.timestampMs()`. | Автомати блокувань і задач не читають годинник вузла. |
| <a id="srs-con-06"></a>SRS-CON-06 | Персональні дані (GDPR, Регламент (ЄС) 2016/679) фреймворк не інтерпретує; журнал, снапшоти й кеш можуть їх містити. | Мінімізація даних у командах і шифрування носіїв – відповідальність застосунку й середовища; у документації застосунку це вказується. |
| <a id="srs-con-07"></a>SRS-CON-07 | Обмеження частоти запитів (rate limiting) клієнтів HTTP фреймворк не виконує. | Зворотний тиск між вузлами – `maxInflightAppends`, `maxEntriesPerAppend`; обмеження частоти – на шлюзі застосунку. |

## 6. Глосарій (Glossary)

| Термін | Визначення |
| :--- | :--- |
| Raft | Алгоритм консенсусу з одним лідером: лідер дописує команди в журнал і реплікує їх; запис зафіксовано, коли він збережений на більшості вузлів. |
| Term | Монотонний номер епохи лідерства; кожні вибори його збільшують. Повідомлення зі старшим term змушує вузол стати фоловером. |
| Commit index | Найбільший індекс запису журналу, відомий як збережений на більшості вузлів; записи до нього застосовуються до автоматів станів. |
| PreVote | Попередній раунд голосування без збільшення term; не дає ізольованому вузлу збільшувати term і зміщувати чинного лідера після повернення. |
| Lease (оренда лідерства) | Інтервал (0,8 × мінімального таймауту виборів) після підтвердження більшістю, протягом якого лідер відповідає на лінеаризовані читання без мережевого раунду. |
| ReadIndex | Лінеаризоване читання: лідер фіксує поточний commit index, підтверджує лідерство раундом heartbeat і відповідає після застосування до цього індексу. |
| Fencing token (маркер огородження) | Число, що строго зростає з кожним наданням блокування (індекс запису журналу); ресурс відхиляє операції з меншим маркером. |
| Snapshot | Серіалізований стан усіх сервісів і таблиці дедуплікації на індексі `lastIncludedIndex`; заміщує записи журналу до цього індексу. |
| mTLS | Взаємна автентифікація TLS: обидві сторони з'єднання пред'являють сертифікати, підписані довіреним центром. |
| HMAC-SHA256 | Код автентифікації повідомлення на основі SHA-256 і спільного секрету; підтверджує, що повідомлення створено власником секрету. |
| Single flight | Об'єднання одночасних промахів кешу за одним ключем в одне завантаження з джерела. |
| Read-your-writes | Гарантія, що клієнт після власного запису читає стан, не старіший за цей запис. |
